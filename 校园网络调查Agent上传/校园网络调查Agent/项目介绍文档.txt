# 校园网络故障调查 AI Agent：项目介绍

> 本文依据“综合项目”中的两张项目说明截图整理。截图未给出的实现细节、角色划分和阶段安排均为设计假设；姓名、学号由提交者自行填写。

## 1. 项目背景与问题

宿舍区网络卡顿可能与链路拥塞、设备故障、无线干扰或路径变化等多种因素有关。单凭用户感受难以确定原因，工程师需要结合拓扑、指标和路径记录排查，并解释判断依据。本项目拟开发一个面向校园网络工程师的调查 Agent，帮助其提出假设、检查证据、记录反证并给出可解释的调查结论与修复建议。

## 2. 用户和使用场景

主要用户为校园网络工程师。典型场景是学生报告宿舍区高时延：工程师输入现象、选择调查案例，系统结合网络数据逐步检查，展示证据、排查过程、可能位置及建议。系统辅助人工判断，不直接对网络设备执行更改。

## 3. 项目目标与预期功能

1. 汇集模拟校园网络拓扑、指标、日志与主动探测结果，支持正常和异常时段的比较。
2. 围绕链路拥塞、设备故障、Wi-Fi 干扰和路径变化等提出假设，寻找支持与反对的证据。
3. 通过交互式拓扑展示调查过程与疑似位置，输出可解释结论、局限和下一步建议。
4. 设计高时延调查专业 Skill，指导检查证据、适用条件和不确定性。

## 4. 数据与方法

按原始材料，拟使用本地 JSON、CSV 格式的模拟校园网络数据，包括网络拓扑、正常与异常时段 RTT、链路容量、流量、利用率、队列指标、丢包率及路径记录。构建拥塞、路径变化、速率下降、误导线索、数据缺失和模型不适用等案例；故障标签与预期判断单独保存，仅用于评测，不向 Agent 开放。

拟采用大语言模型驱动的 ReAct 工具调用机制，依次提出假设、选择工具、分析证据；使用统计比较、路径序列比较，并仅在假设条件满足时使用 M/M/1 排队模型辅助核验时延。证据不足时保留不确定结论，不把模型估计当作真实测量。

## 5. 阶段范围与边界

第一阶段以可运行的前后端闭环为目标：输入现象，获取演示分析结果并展示证据和建议。它使用模拟案例与本地规则，不能访问真实校园网络，也不等同于已经实现的大语言模型 Agent、真实探测或交互式拓扑。完整系统中再逐步接入工具、Skill、模型以及独立评测流程。

## 6. 成功标准与评价计划

最终目标是完成一个可运行的单 Agent 系统，实际调用至少两个功能工具，其中至少一个包含网络计算或检查，并实际使用一个专业 Skill；能完整展示假设、工具调用、证据、反证与结论。设计至少五个不同类型的测试案例，对比直接 LLM、Agent 加 Tools、Agent 加 Tools 加 Skill 三组配置，使用任务成功率、证据完整率等指标记录真实结果，分析至少一个失败或不确定案例，并提供可复现的代码、数据、运行说明和报告。

**评价口径（设计假设）**：任务成功需预先规定每个案例所需的关键判断；证据完整率可定义为结论实际引用的必要证据项数除以该案例预先规定的必要证据项数。案例标签和答案由评测端保管。当前第一阶段不宣称已经完成上述对比或达到最终指标。

## 7. 项目意义

将通信原理与网络排查经验转化为 Agent 可执行的工具和专业 Skill，辅助工程师有依据地定位高时延原因。通过可视化展示工具调用、证据与结论之间的联系，提高调查过程的透明度；通过对照实验检验工具与专业 Skill 对判断和不确定性处理的影响。
